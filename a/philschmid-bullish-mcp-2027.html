Schmid 长文：为什么 2027 年的 MCP 比以往更值得看好

Philipp Schmid 在长文里论证自己为何比以往更看好 MCP：Linear 与 Notion 的智能体已产出约一半 issue，Atlassian 每天超 500 万次工具调用，Neon 用量每周增长 14%。Code Mode、Skills 扩展、Events 事件机制与 MCP Apps 四项演进，正在把 MCP 从远程工具调用推向完整的智能体运行时。

Philipp Schmid（@_philschmid）· 原帖 2026-11-26T13:30:28+00:00 · 收录 2026-11-28T08:35:00+08:00

Philipp Schmid 在一篇长文里说，自己现在比以往任何时候都更看好 MCP。过去 18 个月里，MCP 走完了完整的炒作周期：早期兴奋很快变成反弹与困惑，上下文膨胀是最主要的抱怨；Skills 出现后，大多数开发者转向 CLI 与渐进式披露。Schmid 说自己从不认同那种转向，现在风向正在改变。

大厂的用量数字在往上走

Schmid 先摆了几组用量数字。在 Linear 与 Notion，智能体现在大约产出了一半的 issue（约每周 240 万个）与页面，Notion 报告 MCP 流量增长了 60 倍。在 Atlassian，MCP 每天处理超过 500 万次工具调用，其中 44% 的使用者在软件团队之外，而 CLI 在这些人手里从来不是选项。在 Neon，通过 MCP 的智能体用量每周增长 14%。苹果现在也为 Pages、Numbers 与 Keynote 自带本地 MCP 服务器。

协议本身也在演进。2026 年 7 月 28 日的规范去掉了有状态会话，增加了官方扩展，客户端也在学着更聪明地使用这些扩展。

代码模式：一次脚本代替多轮工具调用

长文的第一组理由是 Code Mode 加结构化输出与多模态。真实任务几乎总要超过一次工具调用，例如先列出未解决的 issue，再取详情、查报错、写总结。普通工具调用每步都要多一轮模型对话，还把信息倒进上下文；跨两个 MCP 服务器拼接数据时，模型的上下文就成了中间结果的临时内存。

Code Mode 改变了调用方式：不再把 50 个工具 schema 塞进提示词、每轮调一个工具，而是给模型一个沙箱，把 MCP 工具暴露成可调用的函数。这已经成为 OpenCode 2.0、Claude Code、OpenAI Codex、Pi 与 Factory Droid 的默认做法。模型在写代码前就知道工具返回什么，效果最好：服务器在 inputSchema 之外声明 outputSchema，客户端可以提前生成类型化桩代码，直接传回结构化内容。模型用一个脚本串起多次调用，在内存里过滤拼接，只把有用的结果返回。

相比 CLI，MCP 服务器天生多模态：一次工具调用可以同时返回代码用的结构化内容，以及独立的图片、音频或嵌入资源块。认证也更干净：CLI 与裸 curl 逼着用户把 API 密钥存在磁盘或环境变量里，权限还很宽；MCP 客户端在沙箱之外处理每用户的 OAuth 2.1 登录流程与按工具划分的权限，连接远程 SaaS 产品不用把原始凭证交给智能体。

Skills 搬进 MCP，版本更新靠摘要

第二组理由是 Skills。Skills 加 CLI 对 MCP 的争论可能就此收尾。过去团队要么发 CLI，要么发 MCP 服务器，还要另外维护 SKILL.md 文件教智能体怎么用。

Skills 扩展（io.modelcontextprotocol/skills）把 Agent Skills 带进了 MCP。每个技能暴露一个 skill:// URI、解析过的 YAML frontmatter，以及带 SHA-256 摘要的文件清单。这些摘要解决了一个长期痛点：团队内技能的更新同步。厂商在服务器上更新技能后，摘要变化，客户端自动拉取新版本，不用再靠手动同步文件。

Anthropic 刚在 Claude 与 Claude Code 上以公开测试版推出 Skills over MCP，Shopify、HubSpot、Atlassian 这类服务器可以按每个登录用户或组织的账号提供定制的操作手册。整个生命周期对上下文很省：连接时，编排器调用 skills/list，只把 frontmatter 里的短名字与描述注入系统指令；智能体需要某个技能时，编排器调用 resources/read（未列出的技能用 skills/get）把完整 SKILL.md 载入上下文，或者按 sha256 摘要把文件缓存到本地路径，供智能体从磁盘读取。

事件机制：智能体可以被动唤醒

第三组理由是常驻与多人协作的 MCP Events。智能体的下一步是多人与常驻工作流。此前 MCP 集成严格是拉取式的：外部系统里发生事情时，无法通知智能体，也无法把它唤醒。

处于测试版的 MCP Events 扩展改变了这一点。服务器在 server/discover 里声明 io.modelcontextprotocol/events，通过 events/list 列出可用事件。编排器可以暴露一个订阅工具（例如 OpenCode 的自动化工具），或者跨服务器响应用户操作，MCP 客户端在后台用三种投递模式之一运行订阅。

Webhook（events/subscribe）：用户不在时，服务器向宿主回调地址发送签名的 HTTP POST 请求。推送（events/stream）：服务器通过一条打开的连接实时流式推送更新，例如构建或部署日志。轮询（events/poll）：客户端按计时器检查，适合没有公开地址的本地 CLI 与桌面应用。

Schmid 举了凌晨 2 点的 P0 安全警报或紧急客户邮件为例。事件触发时，MCP 客户端跟踪游标、按 eventId 去重，把负载交给编排器；编排器唤醒智能体，智能体拉取日志或最近的对话记录，在有人查看收件箱之前先贴出一份分流总结。Shop MCP（订单更新）与 Vercel（deployment.succeeded）等早期服务器已经支持事件。结合 MCP Tasks（io.modelcontextprotocol/tasks），智能体可以处理异步工作流，不用再自己拼 webhook 胶水。

三种模式的延续方式也各不相同。Webhook 到达后，编排器把事件注回同一条轨迹（已订阅的对话线程），或者为每次警报生成一条新的隔离轨迹。推送模式下，本地守护进程如 OpenCode 2.4.0 与 stdio 服务器不用公开地址也能保持连接，MCP 客户端在模型上下文之外保持 events/stream 打开，并跟踪游标心跳以便重连；每条通知追加到当前会话轨迹，或者触发一条新的隔离轨迹。轮询模式下，无状态或无服务器的 MCP 服务器与简单本地 CLI 不用公开地址、不用打开的套接字、不用每客户端服务器状态；模型从不运行轮询循环，MCP 客户端从 cursor: null 开始，在调用之间等待 nextPollMs，并检查 truncated: true 以发现离线期间的缺口；只有当 events 非空时才唤醒智能体。

MCP Apps：交互界面直接嵌进客户端

第四组理由是 MCP Apps。只看原始 JSON 与纯文本不够：想看 p95 延迟图表、过滤实时仪表盘或浏览设计稿时，需要交互界面。MCP Apps（io.modelcontextprotocol/ui）让服务器直接在兼容客户端里返回沙箱化的交互式 HTML 视图（text/html;profile=mcp-app），不用逼用户在 4 个浏览器标签页之间来回切换。Slack 的新 MCP 客户端、Claude 的交互式连接器与 Google Antigravity 已经支持这种模式，在聊天内、发布看板这类侧边面板里，以及自定义文件查看器中内联渲染 MCP Apps。

还缺的三块：可观测性、发现、安全

Schmid 也列了仍需解决的缺口。可观测性与意图：MCP 服务器只看到工具调用，看不到用户的对话。传递 telemetry.intent 元数据，或者暴露 Cloudflare 的 submit_feedback 这类反馈工具会有帮助，但大多数服务器仍然不知道自己为什么被调用。发现：把服务器提交到 5 个不同的注册表无法扩展，需要像 /.well-known 这样更干净的发现模式，加上自动安全扫描。安全：不可信的 webhook 负载、Code Mode 沙箱与嵌入式 UI iframe 都扩大了提示注入的攻击面。

不止是远程工具调用

Schmid 的结论是，MCP 正在越过简单的工具调用。客户端正在长成完整的运行时，把 Code Mode、类型化输出、Agent Skills、异步 Tasks、Events 与嵌入式 UI 合进同一个协议。他认为，2027 年最好的智能体编排器会赢在 MCP 集成上，而且编排器本身也应该成为一个 MCP 服务器。

不用再发明一套自定义多智能体协议：编排器可以暴露自己的 MCP 服务器，让智能体用已经熟悉的原语协调。子智能体以 MCP Tasks 的形式运行；一块共享的 swarm board 暴露工具，供各方贴出发现、认领工作；任务完成或有新进展时，MCP Events 唤醒协调器或对等智能体。

最后他划了一条线：好的 MCP 服务器为智能体暴露工具，而不是把智能体当工具。把整个 SaaS 产品包在一个 ask_agent 端点后面，会饿死智能体本来就有的上下文。常规服务器应该专注于干净的类型化工具与结构化数据，让用户自己的智能体去组合；只有跨子智能体、团队或公司的长期协调，才值得用 agent-as-MCP-server。

2. Native Skills with versioning

The best harnesses will have the best MCP client https://x.com/i/article/2125943030158934016

Why I'm Bullish on MCP for 2027

MCP went through the full hype cycle in the last 18 months. Early excitement turned into backlash and confusion fast, with context bloat as the main complaint. When Skills arrived, most developers moved to CLIs and progressive disclosure instead. I never believed in that, and that sentiment is now changing.

At Linear and Notion, agents now create roughly half of all issues (~2.4M/week) and pages, with Notion reporting 60x MCP traffic growth. At Atlassian, MCP handles over 5M tool calls per workday, and 44% of those users sit outside software teams where CLIs were never an option. At Neon, agent usage over MCP grows 14% week over week, and even Apple now ships local MCP servers for Pages, Numbers, and Keynote.

The protocol is healthy and actively improving. The 2026-07-28 spec dropped stateful sessions and added official extensions, and clients are getting smarter about how they use them.

I'm bullish on MCP going into 2027.

Code Mode, structured outputs, and multimodality

Real tasks almost always take more than 1 tool call, e.g. you list open issues, grab details, check errors, and write a summary.

With plain tool calling, every step needs another model turn and dumps information into the context. Joining data across 2 MCP servers uses the model's context as memory for intermediate payloads.

Code Mode is changing how agents call MCP servers. Instead of putting 50 tool schemas into the prompt and calling 1 tool per turn, the harness gives the model a sandbox and exposes MCP tools as callable functions. It's already becoming the default in OpenCode 2.0, Claude Code, OpenAI Codex, Pi, and Factory Droid.

Code Mode works best when the model knows what a tool returns before writing code. When an MCP server declares outputSchema alongside inputSchema, the client can generate typed stubs upfront and pass back structuredContent directly. The model chains multiple calls in 1 script, filters and joins in memory where compute is cheap, and returns only what matters.

Compared to CLIs, MCP servers are natively multimodal. A tool call can return typed structuredContent for code alongside separate image, audio, or embedded resource blocks.

Auth is also cleaner. CLIs and raw curl force you to store API keys on disk or in environment variables with broad permissions. An MCP client handles per-user OAuth 2.1 login flows and scoped tool permissions outside the sandbox, so connecting a remote SaaS product works without handing raw credentials to the agent.

Skills move inside MCP

The debate of Skills plus a CLI versus MCP might come to an end as well. So far teams shipped CLIs or MCP servers and maintained separate SKILL.md files to teach agents how to use them.

The Skills extension (io.modelcontextprotocol/skills) brings Agent Skills inside MCP. Each skill exposes a skill:// URI, parsed YAML frontmatter, and a file manifest with SHA-256 digests. Those digests solve one of the biggest headaches with Agent Skills: keeping them updated across a team. When a vendor updates a skill on the server, the digest changes and clients pull the new version automatically instead of relying on manual file syncs.

Anthropic just shipped Skills over MCP in public beta across Claude and Claude Code, letting servers like Shopify, HubSpot, and Atlassian serve playbooks tailored to each logged-in user's account or organization.

The lifecycle stays light on context:

On connect, the harness calls skills/list and injects only the short name and description from frontmatter into the system instructions.

When the agent needs a skill, the harness calls resources/read (or skills/get for unlisted skills) to load the full SKILL.md into context, or caches the files to a local path keyed by the sha256 digest so the agent can read them from disk.

Always-on and multiplayer agents with MCP Events

The next step for agents is multiplayer and always-on workflows. Until recently, MCP integrations were strictly pull-based: they couldn't receive notifications or wake an agent up when something happened in an external system.

The MCP Events extension (now in beta) changes that. A server advertises io.modelcontextprotocol/events in server/discover and lists available events via events/list. A harness can expose a subscribe tool (like OpenCode automation tool) or user actions across servers, and the MCP client runs the subscription in the background using 1 of 3 delivery modes:

Webhook (events/subscribe): The server sends signed HTTP POST requests to a host callback URL while the user is away.

Push (events/stream): The server streams live updates over an open connection, like build or deploy logs.

Poll (events/poll): The client checks on a timer. Useful for local CLIs and desktop apps without a public URL.

Take a P0 security alert at 2 a.m. or an urgent customer email. When an event fires, the MCP client tracks the cursor, deduplicates by eventId, and hands the payload to the harness. The harness wakes the agent, which pulls logs or recent thread history and posts a triage summary before anyone checks their inbox. Early servers like Shop MCP (order updates) and Vercel (deployment.succeeded) already ship event support. Combined with MCP Tasks (io.modelcontextprotocol/tasks), agents can handle async workflows without custom webhook glue.

Webhook (events/subscribe)

Remote or durable harnesses like ChatGPT expose a callback endpoint so agents can wake up while you're offline. The model or user sets the event filters and standing instructions once, and the MCP client registers the callback under a renewable TTL.

Continuation: When a webhook POST arrives, the harness injects the event back into the same trajectory (the subscribed chat thread) or spawns a new isolated trajectory per alert.

Push (events/stream)

Local daemons like OpenCode 2.4.0 and stdio servers use push mode to stay connected without a public URL. Once the model or user creates the watch, the MCP client holds events/stream open outside model context and tracks cursor heartbeats for reconnects.

Continuation: Each notification appends to the active session trajectory (like live deploy logs) or triggers a new isolated trajectory (running a prompt, shell command, or Code Mode script).

Poll (events/poll)

Stateless or serverless MCP servers and simple local CLIs use poll mode with no public URL, no open socket, and no per-client server state. The model never runs the poll loop; the MCP client starts from cursor: null, waits nextPollMs between calls, and checks truncated: true for offline gaps.

Continuation: The client wakes the agent only when events is non-empty, resuming the same session trajectory or starting a new task trajectory per batch.

Products are becoming agent-native with MCP Apps

Raw JSON and plain text aren't enough when you want to inspect a p95 latency chart, filter a live dashboard, or browse a design deck. MCP Apps (io.modelcontextprotocol/ui) let servers return sandboxed interactive HTML views (text/html;profile=mcp-app) directly inside compatible clients instead of forcing you across 4 browser tabs.

Slack's new MCP client, Claude's interactive connectors, and Google Antigravity already support this pattern, rendering MCP Apps inline in chat, in side panels like release boards, and as custom file viewers.

What still needs work

There are still real gaps to sort out:

Observability and intent: MCP servers only see tool calls and miss the user's conversation. Passing telemetry.intent metadata or exposing feedback tools like Cloudflare's submit_feedback helps, though most servers still don't know why they were called.

Discovery: Submitting your server to 5 different registries doesn't scale. We need cleaner discovery patterns like /.well-known with automated security scanning.

Security: Untrusted webhook payloads, Code Mode sandboxes, and embedded UI iframes all widen the prompt-injection surface.

Beyond remote tool calls

MCP is moving past simple tool calls. Clients are growing into full runtimes that combine Code Mode, typed outputs, Agent Skills, async Tasks, Events, and embedded UI in 1 protocol.

I think the best agent harnesses in 2027 will win on their MCP integration, and the harness itself should be an MCP server too.

Instead of inventing a custom multi-agent protocol, a harness can expose its own MCP server so agents coordinate with the same primitives they already use. Subagents run as MCP Tasks. A shared "swarm board" exposes tools to post findings and claim work. MCP Events wake the coordinator or peer agents when a task finishes or a new update lands.

Good MCP servers expose tools for agents, not agents as tools. Wrapping an entire SaaS product behind a single ask_agent endpoint starves it of the context your agent already holds. Keep regular servers focused on clean, typed tools and structured data so your own agent can combine them, and reserve agent-as-MCP-server for long-running coordination across subagents, teams, or companies.
